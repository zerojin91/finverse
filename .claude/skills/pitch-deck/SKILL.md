# Pitch Deck — 본선 발표자료 설계

심사위원이 짧은 시간에 이해하고 **질문하게 만드는** 자료. 정보를 다 넣는 게 목표가 아니다.

## 발표 조건 (확정)

**PT 15분 + 질의응답 5분**, 오프라인 발표. 발표는 **PDF 파일로만** 진행한다 — PPT는 기술적 오류 방지를 위해 허용되지 않으므로, 애니메이션·전환·임베드 영상에 의존하는 구성을 만들지 않는다.

15분이면 슬라이드 15~20장 + 라이브 데모 4~5분이 적정하다. 발표 심사는 본선 통과 11팀 내외를 대상으로 하며, 최종 발표자료(PDF)와 소스 코드(ZIP)를 사전 제출한 뒤 진행한다.

## 발표 흐름

```
1. 문제        — 심사위원 본인의 경험으로 만들기
2. 통찰        — 왜 기존 서비스로는 안 되는가
3. 해결 구조   — 시장 시뮬레이션 → 개인 트윈 (한 장)
4. 라이브 데모  — 여기가 중심
5. 데이터·AI 설계 — 데모가 못 보여주는 것
6. 안전 설계   — 수치와 서술의 분리
7. 확장·기대효과
8. 팀·마무리
```

**데모가 중심이다.** 배포 URL이 있는 팀의 최대 무기는 "지금 열어보시면 됩니다"이다. 슬라이드는 데모의 맥락을 만들고, 데모가 보여줄 수 없는 것(데이터 설계, 확장성, 안전 원칙)을 채운다. 슬라이드로 기능을 설명하고 데모를 덧붙이면 순서가 거꾸로다.

## 슬라이드 작성 원칙

**한 장에 메시지 하나.** 발표는 듣는 매체다. 슬라이드에 문장을 채우면 심사위원이 읽느라 발표를 안 듣는다. 슬라이드에는 메시지 한 줄 + 그것을 뒷받침할 시각 요소 하나만 둔다. 나머지는 발표 노트로 뺀다.

**슬라이드 항목 형식:**

```markdown
### S-04 · 라이브 데모 진입

**메시지:** 오늘 시장을 움직인 사건이 내 자산에 어떤 영향을 주는지, 지금 보여드립니다.

**시각 요소:** 배포 앱 시장 인사이트 첫 화면 (전체 화면 전환)

**발표 노트:**
- 여기서 브라우저로 전환. 미리 열어둔 탭 사용, 현장에서 URL 입력 금지
- 시장 연결 5개 항목의 기여도 %p를 짚는다
- (30초)

**시간:** 0:30
```

## 데모 시나리오

**미리 열어둔 탭을 쓴다.** 현장에서 URL을 입력하거나 로딩을 기다리면 발표 흐름이 끊긴다.

데모 경로는 서비스의 핵심 흐름과 같아야 한다:

```
시장 인사이트 (기여도 분해)
  → 발생 가능 이벤트 (조건을 켜고 끄기)
  → 시나리오 상세 (조건부 경로 + 반증 신호)
  → 마이 금융 트윈 (내 자산 경로 변화)
```

**보여줄 것을 미리 정한다.** 클릭 순서와 각 화면에서 말할 한 문장을 적어둔다. 즉흥 탐색은 반드시 막힌다.

**미구현 영역은 들어가지 않는다.** 눌러도 아무 일이 안 일어나는 버튼을 시연하면 그 순간 신뢰가 사라진다. 데모 경로는 `[구현됨]` 기능만 지난다.

## 예상 질의응답

**가장 어려운 질문을 먼저 준비한다.** 이 프로젝트에서 반드시 나오는 질문:

| 예상 질문 | 답변 방향 |
|----------|----------|
| 화면의 숫자는 실제 데이터인가, 하드코딩인가 | 회피하지 않는다. 현재는 온톨로지 규칙에 맞춰 사전 산출·검증한 값이며 런타임 생성이 아니라고 명시. 이어서 데이터 계층 설계와 다음 단계를 제시 |
| 생성형 AI가 주가를 예측하는 것 아닌가 | 수치는 규칙 기반 엔진이 산출하고 AI는 설명·구조화·편향 코칭만 한다는 분리 원칙. 이게 안전장치이자 차별점 |
| 예측이 틀리면 책임은 | 예측이 아니라 조건부 밴드 + 반증 신호. "이 시나리오가 틀렸다는 걸 언제 알 수 있는가"를 같은 비중으로 보여주는 설계 |
| 기존 증권사 앱이 만들면 되는 것 아닌가 | 증권 앱은 실행이 목적이라 "결정 전 비교"와 "편향 지적"에 구조적 이해 상충. B2B2C 도입 채널로 협업 모델 제시 |
| 수익 모델은 | B2B2C 기관 라이선스, 교육형 스폰서 시나리오 |
| 사용자가 왜 재방문하는가 | 시장 사건이 계속 발생하고, 편향 교정은 1회로 끝나지 않는 반복 훈련 |

답변은 **30초 이내로 준비한다.** 길어지면 다음 질문 기회를 잃는다.

## 산출물 구조

`_workspace/04_deck_builder_deck.md`에 다음을 담는다:

```markdown
# FINVERSE 본선 발표자료
> 가정: 발표 8분 + 질의 5분

## 1. 발표 흐름 요약 (슬라이드 목록 + 시간 배분)
## 2. 슬라이드별 상세 (S-01 ~ S-NN)
## 3. 데모 시나리오 (클릭 경로 + 화면별 대사 + 사전 준비물)
## 4. 예상 질의응답
## 5. 리스크와 대비 (데모 실패 시 대체 경로 등)
```

**데모 실패 대비를 반드시 넣는다.** 네트워크가 끊기거나 배포가 다운되면 대체할 화면 캡처를 미리 준비한다.

## 작성 원칙

수치는 원장에서만 가져온다. **발표에서 잘못 말한 숫자는 정정할 기회가 없다.**

기획서·명세서와 기능 명칭을 통일한다. 세 문서가 같은 기능을 다르게 부르면 심사위원이 다른 기능으로 인식한다.
