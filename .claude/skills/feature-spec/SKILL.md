# Feature Spec — MVP 기능명세서 작성

심사위원이 "이 팀이 실제로 무엇을 만들었는가"를 확인하는 문서. 배포 URL을 열어놓고 대조하며 읽는다는 전제로 쓴다.

## 기능 ID 체계

화면 접두사 + 순번. 문서 전체에서 이 ID로만 기능을 지칭한다.

| 접두사 | 화면 |
|--------|------|
| `MI-` | 시장 인사이트 (Market Insight) |
| `SC-` | 시나리오 (라이브러리·상세·빌더) |
| `TW-` | 마이 금융 트윈 (Twin) |
| `CM-` | 공통 (레이아웃, 내비게이션) |

## 기능 항목 템플릿

기능 하나당 이 표를 채운다. 빈 칸을 남기지 않는다 — 채울 수 없으면 "해당 없음"이라고 쓴다.

```markdown
### MI-01 · 시장 연결

| 항목 | 내용 |
|------|------|
| 목적 | KOSPI 변동을 구성 요소별 기여도로 분해해 "무엇이 얼마나 끌어내렸는가"를 보여준다 |
| 화면 위치 | 시장 인사이트 상단 |
| 입력 | 없음 (진입 시 자동 표시) |
| 출력 | 5개 구성요소의 현재가·등락률·KOSPI 기여도(%p) |
| 상태 전이 | 없음 |
| 사용 데이터 | 종목 시세, 환율, 투자자별 수급, 업종 지수 |
| 구현 상태 | 구현 완료 |
| 예외 | 해당 없음 |
| 근거 | 사실 원장 MI-01 |
```

## 구현 상태 표기

| 표기 | 기준 |
|------|------|
| 구현 완료 | 배포 앱에서 사용자가 직접 확인·조작 가능 |
| 부분 구현 | UI는 있으나 동작이 목업 (버튼은 있는데 계산이 없음) |
| 계획 | 설계만 존재, 코드에 대응물 없음 |

**정직한 상태 표기가 과장보다 강하다.** 코드 ZIP이 함께 제출되므로 과장은 반드시 발각된다. 현재 배포본에서 데이터 파이프라인·시뮬레이션 엔진·LLM 연동은 미구현이다. 이를 "구현 완료"로 쓰면 나머지 명세의 신뢰도까지 함께 무너진다.

대신 이렇게 쓴다: 무엇이 동작하고, 무엇이 사전 산출값이며, 그 값이 어떤 규칙으로 검증되었고, 다음 단계가 무엇인지. 심사위원은 MVP에 미구현이 있다는 사실보다 팀이 그것을 알고 있는지를 본다.

## 문서 구조

```markdown
# FINVERSE MVP 기능명세서
> 기준일 | 배포 URL | 대상 시장·기간

## 1. 개요
- 서비스 한 줄 정의
- MVP 범위 (무엇을 검증하는가)
- 화면 구조 (2개 탭)

## 2. 정보 구조 및 사용자 흐름
(핵심 흐름 다이어그램 1개)

## 3. 기능 명세
### 3.1 시장 인사이트 (MI-*)
### 3.2 시나리오 (SC-*)
### 3.3 마이 금융 트윈 (TW-*)
### 3.4 공통 (CM-*)

## 4. 데이터 설계
- 4개 도메인과 수집원
- 저장 규칙 (출처·수집 시각·영향 방향 병기)

## 5. AI 적용 설계
- 역할별 적용 화면 매핑
- 수치와 서술의 분리 원칙

## 6. 구현 상태 요약
| 기능 ID | 명칭 | 상태 |
(전체 기능의 상태를 한 표로 — 심사위원이 가장 먼저 보는 표)

## 7. 안전 설계 및 제약
```

## 작성 원칙

**화면에서 확인 가능한 단위로 쪼갠다.** 기능 ID는 실제 화면 영역과 1:1로 대응해야 한다. 코드의 내부 함수 단위로 쪼개면 심사위원이 화면에서 찾을 수 없다.

**기능명은 UI 표기 그대로 쓴다.** 화면에 「시장 연결」이라고 표시되면 명세서도 "시장 연결"이다. "마켓 커넥션 패널" 같은 재작명은 대조를 방해한다.

**PRD를 복사하지 않는다.** `docs/PRD.md`는 내부 설계 문서라 비목표·기술 스택·로드맵 비중이 크다. 명세서는 화면별 기능 정의가 중심이고, 심사에 필요 없는 내부 논의는 덜어낸다.

**AI 역할은 화면에 매핑한다.** "LLM이 요약한다"가 아니라 "역할 A(이해) → MI-02 AI 요약 영역"으로 쓴다. 매핑되지 않는 AI 역할은 `계획` 상태다.

**수치는 원장에서만 가져온다.** 원장에 없으면 fact-curator에게 등재를 요청한다.

## 자주 나오는 결함

| 결함 | 왜 문제인가 |
|------|-----------|
| 기획서에 있는 기능이 명세에 없음 | 두 문서를 나란히 보는 심사에서 즉시 드러난다 |
| 입력 칸이 비어 있음 | 정적 표시물인지 조작 가능한지 구분 불가 |
| 구현 상태 없이 기능만 나열 | MVP 명세서의 존재 이유가 사라진다 |
| 기능명이 화면 표기와 다름 | 배포 URL과 대조가 불가능해진다 |
