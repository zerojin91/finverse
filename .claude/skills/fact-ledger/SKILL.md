# Fact Ledger — 사실 원장 구축

공모전 산출물 여러 개가 서로 다른 숫자를 말하는 사고를 구조적으로 막는 장치. 모든 문서가 이 원장 하나만 인용하면 불일치가 발생할 수 없다.

## 왜 원장인가

FINVERSE의 화면 수치는 전부 `app/page.tsx`에 하드코딩된 사전 산출값이다. 문서 작성자가 각자 코드를 읽으면 서로 다른 값을 인용하거나, 코드에 없는 값을 만들어낸다. 원장은 "무엇이 사실인가"를 한 곳에서 판정한다.

## 원장 스키마

`_workspace/01_fact_curator_ledger.md`에 다음 구조로 작성한다.

```markdown
# FINVERSE 사실 원장
> 기준일: YYYY-MM-DD | 배포 앱 검증: 완료 / 미수행

## 1. 핵심 수치

| 항목 | 값 | 상태 | 출처 |
|------|-----|------|------|
| KOSPI 종가 | 6,023.66 | [구현됨] | app/page.tsx:60 |
| 일간 변동률 | -10.84% | [구현됨] | 배포앱 KOSPI LIVE |

## 2. 화면·기능 목록

| 기능 ID | 화면 | 기능명(UI 표기 그대로) | 상태 | 출처 |
|---------|------|---------------------|------|------|
| MI-01 | 시장 인사이트 | 시장 연결 | [구현됨] | app/page.tsx:49 |

## 3. 데이터 출처

| 도메인 | 수집원 | 상태 | 출처 |
|--------|--------|------|------|
| 시장 | KRX Data Marketplace | [계획] | docs/ontology/finverse-ontology.md:43 |

## 4. 기술 스택

| 계층 | 값 | 출처 |
|------|-----|------|

## 5. 표현 규칙

### 쓸 수 있는 표현
- "조건부 경로", "신뢰구간", "~가 확인되면", "교육용 가상 시나리오"

### 쓸 수 없는 표현
- "예측한다", "~까지 오른다" 등 단정형 → 이유: 금융 안전 원칙 위반이자 서비스의 핵심 차별점 자기부정
- "추천 종목", "매수 시점" 등 상품·매매 권유
- 미구현 기능에 대한 완료형 서술

## 6. 미확정 / 사용자 확인 필요

| 항목 | 왜 확정 불가 | 필요한 조치 |
|------|------------|-----------|

## 7. 충돌 기록

| 항목 | 값 A (출처) | 값 B (출처) | 판정 |
|------|-----------|-----------|------|
```

## 상태 태그

| 태그 | 의미 | 판정 기준 |
|------|------|----------|
| `[구현됨]` | 배포 앱에서 사용자가 직접 확인 가능 | 화면에 렌더링되고 상호작용이 동작 |
| `[부분]` | UI는 있으나 동작이 목업 | 버튼은 있는데 눌러도 계산이 없는 경우 등 |
| `[계획]` | 문서에만 존재 | 코드에 대응물 없음 |

이 구분이 원장의 존재 이유 중 절반이다. 현재 배포본은 데이터 파이프라인·시뮬레이션 엔진·LLM 연동이 미구현이므로, 관련 사실은 대부분 `[계획]`이다. 이를 `[구현됨]`으로 올리면 코드 ZIP을 함께 제출하는 심사에서 발각된다.

## 추출 절차

1. **코드에서 수치 추출** — `app/page.tsx`의 데이터 리터럴(`marketConnections`, `actualPath`, `scenarios`, `holdings`)에서 값과 라인 번호를 수집한다.
2. **UI 문자열 추출** — 기능명은 코드의 한국어 레이블을 **그대로** 옮긴다. 문서가 기능을 다르게 부르면 심사위원이 다른 기능으로 인식한다.
3. **배포 앱 대조** — `https://finverse-ai-kr.vercel.app`을 열어 코드값이 실제로 렌더링되는지 확인한다. 접근 실패 시 원장 상단에 명시하고 코드 기준으로 진행한다.
4. **문서에서 계획 추출** — `docs/ontology/`, `docs/PRD.md`, `README.md`에서 데이터 출처와 향후 계획을 `[계획]` 태그로 수집한다.
5. **테스트 파일 확인** — `tests/rendered-html.test.mjs`는 화면에 반드시 존재해야 하는 문자열과 존재하면 안 되는 문자열을 단언한다. 의도된 UI 상태의 근거로 쓸 수 있다.

## 등재 요청 심사

팀원이 새 사실의 등재를 요청하면:

| 상황 | 조치 |
|------|------|
| 코드·앱·문서에서 출처를 찾음 | 등재하고 요청자에게 통지 |
| 출처가 없으나 기존 사실에서 산술 도출 가능 | 도출 과정을 출처란에 적어 등재 (예: `6,023.66 × 1.245 = 7,499.4 → 7,500`) |
| 출처가 전혀 없음 | **거부**. 그 수치 없이 서술할 방법을 제안 |
| 사용자만 아는 정보 (팀원 실명, 발표 시간) | 6번 섹션에 올리고 리더에게 사용자 확인 요청 |

## 갱신 규칙

원장이 바뀌면 그 사실을 인용 중인 팀원에게만 개별 통지한다. 전체 브로드캐스트는 초판 배포 1회로 제한한다 — 브로드캐스트는 비용이 높고, 관련 없는 팀원의 컨텍스트를 오염시킨다.

갱신된 항목에는 `[갱신 YYYY-MM-DD]`를 붙여 QA가 재검증 대상을 식별할 수 있게 한다.
