# Doc Consistency Check — 산출물 경계면 검증

문서 각각의 품질이 아니라 **문서들 사이의 연결 지점**을 본다.

## 왜 경계면인가

기획서와 발표자료가 각각 잘 쓰여 있어도, 하나는 "시나리오 3종", 다른 하나는 "5종"이라 하면 심사에서 무너진다. 각 문서를 따로 읽으면 둘 다 정상으로 보인다. **한쪽만 읽어서는 절대 못 잡는다.** 반드시 양쪽을 동시에 열어 비교한다.

## 검증 대상 경계면

| # | 경계면 | 왼쪽 (생산자) | 오른쪽 (소비자) |
|---|--------|-------------|---------------|
| B1 | 수치 | 사실 원장의 값 + 출처 | 각 문서에 등장하는 모든 숫자 |
| B2 | 구현 상태 | `app/page.tsx` 실제 구현 / 배포 URL 화면 | 문서의 "구현 완료" 주장 |
| B3 | 기능 집합 | 기획서가 언급한 기능 | 명세서의 기능 ID 목록 |
| B4 | 기능 명칭 | 코드의 UI 한국어 레이블 | 문서·발표자료의 기능명 |
| B5 | 표현 규칙 | 원장의 표현 규칙 섹션 | 각 문서의 서술 문장 |
| B6 | 최종 산출물 | `_workspace/`의 초안 md | 생성된 HWPX/PDF의 실제 내용 |
| B7 | 양식 충족 | 공모전 양식이 요구한 항목 | 기획서가 실제로 답한 내용 |

## 검증 절차

### B1 · 수치 정합성 (최우선)

1. 각 문서에서 숫자를 포함한 문장을 전부 추출한다 (`grep -nE '[0-9]'`)
2. 각 숫자를 원장과 대조한다
3. 분류:

| 판정 | 조건 | 심각도 |
|------|------|--------|
| 원장 미등재 | 원장에 없는 숫자 | 높음 |
| 수치 불일치 | 원장에 있으나 값이 다름 | 치명 |
| 문서 간 충돌 | 두 문서가 같은 항목에 다른 값 | 치명 |
| 판정 보류 | 원장이 아직 그 항목을 안 다룸 | — (fact-curator에게 등재 요청) |

단위와 부호도 본다. `-10.84%`와 `10.84% 하락`은 같지만 `732.09p`와 `732.09%`는 다르다.

### B2 · 구현 상태 정합성

이 하네스에서 **가장 가치가 큰 검증**이다. 코드 ZIP이 함께 제출되므로 과장은 반드시 발각된다.

1. 문서에서 완료형 서술을 찾는다 — "구현했다", "제공한다", "분석한다", "생성한다"
2. 각 서술의 대상 기능을 원장의 상태 태그와 대조한다
3. `[계획]` 또는 `[부분]`인데 완료형으로 서술 → **과장** 결함

현재 배포본에서 데이터 파이프라인·시뮬레이션 엔진·LLM 연동은 미구현이다. 이 영역에 대한 완료형 서술은 전부 검토 대상이다.

### B3 · 기능 집합 정합성

1. 기획서가 언급한 기능을 목록화한다
2. 명세서의 기능 ID 목록과 집합 비교한다
3. 양방향 차집합을 모두 보고한다:
   - 기획서에 있고 명세서에 없음 → 명세 누락
   - 명세서에 있고 기획서가 언급 안 함 → 기획서가 성과를 빠뜨림 (역시 결함)

### B4 · 기능 명칭

코드의 UI 레이블을 기준으로 문서의 기능명을 대조한다. 심사위원은 배포 URL을 열어 문서와 대조하므로, 이름이 다르면 다른 기능으로 인식한다.

### B5 · 표현 규칙

원장의 "쓸 수 없는 표현" 목록을 각 문서에 대해 검색한다. 특히 단정형 예측(`~까지 오른다`, `예측한다`)과 상품·매매 권유 표현.

### B6 · 최종 산출물

초안 md와 실제 생성된 HWPX/PDF의 내용이 같은지 확인한다. 생성 파이프라인이 텍스트를 누락하거나 잘라먹을 수 있다. HWPX는 zip이므로 `Contents/section0.xml`의 `<hp:t>` 텍스트를 추출해 대조한다.

### B7 · 양식 충족

공모전 양식의 각 항목이 요구한 질문에 실제로 답했는지 확인한다. 특히 놓치기 쉬운 것:
- 3번: 특정 금융 고객과 **채널을 선택한 배경과 이유**
- 4번: **기존 금융 앱 대비** 차별성 (비교 대상 명시)
- 5번: AI가 서비스 내에서 수행하는 역할을 **구체적으로**
- 6번: **금융 서비스 외 영역** 확장 가능성

## 작업 원칙

**"있는가"가 아니라 "일치하는가"를 묻는다.**

| 약한 질문 | 강한 질문 |
|----------|----------|
| 기획서에 데이터 출처가 언급되었는가 | 기획서와 명세서가 언급한 출처가 같은 집합인가 |
| 기능이 명세되어 있는가 | 명세된 기능이 배포 앱에서 실제 동작하는가 |
| 수치가 있는가 | 그 수치가 원장의 값과 같고 출처가 추적되는가 |

**점진적으로 검증한다.** 문서가 다 끝난 뒤 한 번에 보지 않는다. 각 초안이 완성될 때마다 즉시 원장과 대조한다. 초기 불일치가 뒤 문서로 전파되면 수정 비용이 배로 커진다.

**직접 고치지 않는다.** 수정은 작성자의 몫이다. 다만 어떻게 고칠지는 구체적으로 제시한다.

**판정 보류를 통과로 바꾸지 않는다.** 원장에 없어서 판단할 수 없는 값은 fact-curator에게 등재를 요청하고, 등재될 때까지 보류로 남긴다. 임의 판단은 원장 체계를 무너뜨린다.
