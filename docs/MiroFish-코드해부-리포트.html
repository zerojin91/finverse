01

이 서비스는 무엇을 하는가

코드를 읽기 전에, 이 시스템이 사용자에게 약속하는 것과 실제로 계산하는 것을 분리해 둡니다.

MiroFish는 "만약 이렇게 되면 어떻게 될까"를 시뮬레이션으로 답하는 엔진입니다. 사용자가 하는 일은 두 가지뿐입니다 — 자료를 올리고, 알고 싶은 것을 자연어로 적는 것. 그 뒤로는 파라미터 설정 화면이 없습니다. 에이전트를 몇 명 만들지, 며칠치를 굴릴지, 누가 언제 활동할지를 전부 LLM이 결정합니다. 이 "설정 없음"이 제품의 핵심 주장이고, 동시에 코드 복잡도의 대부분이 여기서 나옵니다.

Fig 01 사용자 관점의 입출력. 중앙 블록은 디스크 위에 실제로 만들어지는 파일들입니다.

세 가지 핵심 주장

주장 1 창발

개별 에이전트에게 결말을 지시하지 않습니다. 각자 페르소나대로 행동하게 두고, 집단에서 나타나는 패턴을 결과로 봅니다.

주장 2 시간 축

Zep 그래프가 "지금 유효한 사실"과 "과거엔 사실이었던 것"을 구분합니다. 여론이 뒤집히는 순간을 추적할 수 있습니다.

주장 3 개입 가능

시뮬이 도는 중에 특정 에이전트에게 질문을 던지거나 사건을 주입할 수 있습니다. 사후 분석이 아니라 실시간 관측입니다.

이 시스템이 하지 않는 일

  • 데이터를 수집하지 않습니다. 크롤러도 API 커넥터도 없습니다. 이미 정리된 문서를 받는 것에서 시작합니다. README의 우한대 데모도 BettaFish라는 별개 프로젝트가 만든 리포트를 씨앗으로 넣은 것입니다.
  • 확률을 계산하지 않습니다. 출력에 신뢰구간이나 확률값이 없습니다. 시나리오 서술이 나옵니다.
  • 같은 입력에 같은 출력을 주지 않습니다. 에이전트 선정이 random.sample 기반이고 시드 고정 코드가 없습니다 — 8장에서 자세히 다룹니다.
  • 백테스트를 제공하지 않습니다. 과거 사건으로 정확도를 검증하는 코드나 데이터셋이 레포에 없습니다.
02

전체 파이프라인

README는 5단계라고 말하지만, 코드는 8개의 뚜렷한 국면으로 나뉩니다. 이후 4~11장이 이 8개를 하나씩 따라갑니다.

Fig 02 왼쪽 점은 각 단계가 어떤 외부 서비스를 건드리는지 표시합니다. 8단계만 셋 다 씁니다.

여기서 눈여겨볼 것 5단계와 7단계가 동시에 돌아갑니다. 시뮬레이션이 라운드를 굴리는 동안 별도 워커 스레드가 그 결과를 계속 그래프에 밀어넣습니다. 그래서 8단계의 리포트 에이전트가 검색을 시작할 때, 그래프는 이미 "원본 자료 + 시뮬레이션 중 벌어진 사건"을 모두 담고 있습니다. 이 되먹임 구조가 이 프로젝트에서 가장 특징적인 설계입니다.

04

온톨로지 생성

services/ontology_generator.py · 732줄 · 그중 절반이 프롬프트 하나

첫 단계에서 시스템이 던지는 질문은 "이 문서에 무엇이 있는가"가 아니라 "이 문서에서 누가 트위터 계정을 가질 수 있는가"입니다. 이 질문 하나가 이후 모든 단계의 성격을 결정합니다.

정확히 10개, 마지막 둘은 고정

프롬프트는 엔티티 타입 개수를 협상 불가능하게 못박습니다. 그리고 그중 마지막 두 개는 항상 Person과 Organization입니다.

Fig 05 슬롯 1–8의 이름은 문서마다 달라지지만 9–10은 항상 같습니다. 관계 타입은 6–10개, UPPER_SNAKE_CASE 강제.

엔티티가 될 수 있는 것과 없는 것

프롬프트에서 가장 많은 분량을 쓰는 규칙입니다. 지식그래프 일반론에서는 "학술 정직성" 같은 개념도 훌륭한 노드지만, 여기서는 발언할 수 없는 것은 노드가 될 수 없습니다. 모든 노드가 나중에 계정으로 변환되기 때문입니다.

허용 — 발언할 수 있는 주체

구체적 개인(공인·당사자·오피니언 리더·전문가·일반인), 기업과 공식 계정, 조직(대학·협회·NGO·노조), 정부·규제 기관, 미디어(신문·방송·1인 미디어), 소셜 플랫폼 자체, 특정 집단의 대표(동문회·팬덤·권익 단체).

금지 — 추상 개념

"여론", "정서", "트렌드" 같은 추상 개념. "학술 정직성", "교육 개혁" 같은 주제·화제. "찬성측", "반대측" 같은 입장·태도. 이것들은 시뮬레이션 결과로 나와야 할 것이지 입력이 아닙니다.

긴 문서를 다루는 법

LLM에 넘기는 텍스트 상한은 MAX_TEXT_LENGTH_FOR_LLM = 50000자입니다. 흔한 구현은 앞에서 5만 자를 자르고 마는데, 여기서는 그렇게 하지 않습니다.

Fig 06 홍루몽 전체 결말을 추론하는 데모가 성립하려면 이 로직이 반드시 필요합니다.

세부 방어 장치 두 가지

1 · 예약어 회피

Zep에는 시스템이 선점한 필드명이 있습니다. LLM이 무심코 name이나 summary를 속성으로 만들면 인제스천이 깨집니다. utils/ontology.py가 이 목록을 들고 있고, safe_attr_name()이 충돌하면 entity_ 프리픽스를 붙여 우회합니다.

uuidnamegroup_idgraph_idname_embeddingsummarycreated_at

2 · max_tokens를 일부러 비움

LLM 호출부에 max_tokens=None이 명시돼 있고, 바로 위에 이유가 주석으로 붙어 있습니다 — 일부 OpenAI 호환 프로바이더가 숨겨진 추론 토큰을 같은 예산에 계산하기 때문에, 4096 같은 값을 박아두면 정작 JSON이 잘려 나옵니다. 그래서 프로바이더 기본값에 맡깁니다. 

result = self.llm_client.chat_json(
    messages=messages,
    temperature=0.3,
    # Structured ontology responses can exceed 4096 completion tokens,
    # especially when a compatible provider counts hidden reasoning in
    # the same budget. Let the provider use its model-specific limit.
    max_tokens=None,
    max_attempts=2,
)
언어 정책 타입 이름은 무조건 영어(PascalCase / UPPER_SNAKE_CASE / snake_case)로 강제하고, description과 analysis_summary만 로케일 언어로 씁니다. 스키마는 안정적으로, 설명은 읽기 좋게 — 합리적인 분리입니다.

지식그래프 구축

services/graph_builder.py · 879줄 · 이 코드베이스에서 가장 영리한 함수가 여기 있습니다

LLM이 뱉은 JSON을 파이썬 클래스로 찍어내기

Zep SDK는 온톨로지를 Pydantic 모델로 요구합니다. 그런데 스키마는 문서마다 LLM이 매번 다르게 만듭니다. 정적으로 클래스를 선언해 둘 방법이 없습니다. set_ontology()는 type()으로 런타임에 클래스를 생성해 이 문제를 넘습니다.

Fig 07 "LLM이 스키마를 만들고 그 스키마로 다시 LLM이 추출한다"는 구조를 성립시키는 12줄.

청킹부터 인제스천까지

Fig 08 인제스천은 비동기라 _wait_for_batch()와 _wait_for_episodes()가 완료를 폴링합니다.

백그라운드 스레드와 로케일 함정

그래프 구축은 오래 걸리므로 build_graph_async()가 태스크 ID만 반환하고 데몬 스레드로 넘깁니다. 그런데 이 코드베이스의 로케일은 스레드로컬이라, 그냥 스레드를 띄우면 워커 안에서 언어 설정이 사라집니다. 그래서 스폰 직전에 값을 캡처해 인자로 넘깁니다. 

# Capture locale before spawning background thread
current_locale = get_locale()

thread = threading.Thread(
    target=self._build_graph_worker,
    args=(task_id, text, ontology, graph_name,
          chunk_size, chunk_overlap, batch_size, current_locale)
)
thread.daemon = True
thread.start()
같은 패턴이 세 번 반복됩니다 graph_builder의 스레드, oasis_profile_generator의 ThreadPoolExecutor 워커, simulation_runner의 모니터 스레드 — 모두 get_locale() → 전달 → set_locale() 3단 패턴을 씁니다. 실제로 한 번 겪고 나서 전체에 적용한 흔적으로 읽힙니다.

Zep 재검색으로 인물 부풀리기

노드의 summary 필드만 보고 페르소나를 만들면 밋밋해집니다. _search_zep_for_entity()가 인물 이름으로 엣지 검색과 노드 검색을 병렬로 한 번 더 돌려서, 그래프 곳곳에 흩어진 그 인물 관련 사실을 긁어모은 뒤 프롬프트에 넣습니다. 사실상 페르소나 생성용 미니 RAG입니다.

병렬 생성 — 순서 보존과 실시간 중계

Fig 10 매번 전체 파일을 다시 쓰는 건 비효율이지만, 덕분에 대기 화면이 볼거리가 됩니다. UX를 위해 성능을 내준 명시적 선택입니다.

LLM을 못 믿는 코드

이 파일에 특히 방어 코드가 몰려 있습니다. 세 겹입니다.

  • _fix_truncated_json() — 응답이 중간에 끊긴 JSON을 닫아서 살려냅니다.
  • _try_fix_json() — 문자열 값 안에 이스케이프 안 된 raw 개행이 들어간 경우를 정규식으로 교정합니다. fix_string_newlines() 헬퍼가 내부에 있습니다.
  • 그래도 실패하면 예외를 던지지 않고 엔티티 summary로 최소 프로필을 만들어 진행합니다. 500명 중 3명이 실패해도 시뮬레이션은 돕니다.
  • __post_init__의 _coerce_to_str() / _coerce_to_str_list() — LLM이 문자열 자리에 dict나 배열을 넣는 경우를 경계에서 한 번에 정규화합니다.

시간 모델 — 의도와 실제가 다른 곳

TimeSimulationConfig에는 하루를 네 구간으로 나눈 활동 배수가 정의돼 있습니다. 주석에 "중국인 작息 습관 기준"이라고 명시돼 있고, 값도 그에 맞습니다 — 새벽엔 사실상 정지(×0.05), 저녁 7~10시가 정점(×1.5).

그런데 실제 러너 스크립트는 네 구간 중 둘만 읽습니다. run_reddit_simulation.py·run_twitter_simulation.py·run_parallel_simulation.py 세 곳 모두 peak과 off_peak만 분기하고 나머지는 else: multiplier = 1.0으로 처리합니다. 설정 JSON에는 morning_activity_multiplier와 work_activity_multiplier가 정상적으로 기록되지만, 읽는 사람이 없습니다.

Fig 12 점선이 TimeSimulationConfig가 기술한 곡선, 막대가 러너가 실제로 계산하는 값입니다.

확인된 불일치 두 가지 ① morning_activity_multiplier(0.4)와 work_activity_multiplier(0.7)는 설정 생성기에서만 등장하고 backend/ 어디에서도 소비되지 않습니다. 프롬프트로 LLM에게 값을 물어보고, dataclass에 담고, JSON으로 저장까지 하지만 읽지 않습니다.
② off_peak_activity_multiplier의 기본값이 설정 생성기는 0.05, 러너 .get() 폴백은 0.3으로 다릅니다. 설정 JSON이 항상 값을 채우므로 실사용에서 드러나진 않지만, 설정 없이 스크립트를 직접 돌리면 새벽 활동이 6배가 됩니다.

총평

27,787줄을 다 읽고 남는 인상

이 코드베이스는 "LLM 출력은 믿을 수 없다"는 전제 위에 세워져 있습니다. 거의 모든 경계마다 정규화, JSON 수선, 룰 기반 폴백, 재시도가 겹겹이 깔려 있고, 프로바이더 호환성 문제를 만날 때마다 대응 코드를 덧댄 흔적이 명확합니다. 실험실 코드가 아니라 사용자에게 노출되고 나서 계속 고쳐진 코드입니다.

잘 만든 부분

  • 동적 온톨로지 — LLM이 만든 스키마로 Pydantic 클래스를 찍어 다시 LLM 추출에 쓰는 구조가 깔끔합니다.
  • 멱등성 — 청크 해시 기반 operation_id로 재시도가 그래프를 오염시키지 않습니다.
  • 프로세스 위생 — atexit+시그널, SIGTERM 후 강제 종료, 앱 팩토리 레벨 훅 등록.
  • 되먹임 그래프 — 시뮬 결과를 문장으로 바꿔 역주입하는 발상과, 그걸 활용하는 PanoramaSearch가 한 쌍으로 설계돼 있습니다.
  • 검색 강제 — min_tool_calls=3으로 근거 없는 서술을 산술적으로 막았습니다.
  • 실패 내성 — 500명 중 몇 명의 페르소나 생성이 실패해도 전체가 멈추지 않습니다.

구조적 한계

  • 단일 프로세스 전제 — 상태를 클래스 변수와 프로세스 로컬 락에 두어 gunicorn 멀티 워커로 띄우는 순간 깨집니다. "dev 서버를 쓴다"보다 깊은 문제입니다.
  • 재현 불가 — 라운드마다 난수 3회, 시드 고정 없음. 결과 하나를 예측으로 인용할 수 없습니다.
  • 라우트 비대 — api/simulation.py 2,878줄. 서비스 계층이 있는데도 로직이 상당수 라우트에 남아 있습니다.
  • 죽은 설정 — 7장의 아침·근무 시간대 배수는 생성·저장되지만 아무도 읽지 않습니다.
  • 클라우드 락인 — Zep Cloud 외의 선택지가 코드 레벨에서 차단돼 있습니다.
  • 검증 공백 — 테스트 18개 중 9개가 Zep 계약. 시뮬 루프와 리포트 로직은 사실상 미커버이고, 예측 정확도 검증은 아예 없습니다.
  • 지역성 — 기본 시간 모델이 중국 생활 패턴이고, 프롬프트가 중국어로 소스에 하드코딩돼 있습니다.

멀티에이전트 시뮬레이션 + 시간축 지식그래프를 실제로 결합한 드문 사례입니다. 아이디어를 가져오기 좋습니다.

안 맞음프로덕션 SaaS

인증·멀티테넌시·수평 확장이 전부 없습니다. 얹는 게 아니라 아키텍처를 다시 짜야 하는 수준입니다.

결과를 읽을 때 이 엔진이 만드는 것은 정교하게 근거를 갖춘 시나리오이지 확률적 예측이 아닙니다. 난수가 세 겹으로 들어가고 백테스트가 없다는 두 사실만으로도, 한 번의 실행 결과를 의사결정 근거로 삼는 건 위험합니다. 같은 설정으로 여러 번 돌려 어떤 결말이 반복되는지 보는 게 이 도구의 올바른 사용법에 가깝습니다.
